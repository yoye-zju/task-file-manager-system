## 1. 产品概述

### 1.1 背景与痛点

传统任务管理工具（看板、甘特图、OKR 平台）存在两个核心问题：

| 痛点 | 具体表现 |
|------|----------|
| **看不到全局** | 任务散落在不同列表/项目，缺乏统一俯瞰视角；不知道整体进展、哪些在阻塞、哪些超期 |
| **看不到逻辑关系** | 任务之间的时间先后、优先级层级、依赖分支无法直观表达；层级目标（Object→KR→Target→Task）与执行任务之间的映射断层 |

### 1.2 产品定位

**AI 任务透视镜** 是一个纯前端项目管理可视化工具。它以"四层层级系统"为核心数据模型，通过五种互补视图实现从宏观目标到微观任务的穿透式管理，并内置中文 NLP 解析引擎辅助快速录入。v3.0 新增飞书多维表格双向同步能力；v4.0 新增时间戳唯一标识体系、编辑弹窗 UI/UX 全面优化、同步进度实时显示、同步超时重试机制。

### 1.3 目标用户

- 独立项目管理者 / 技术负责人
- 需要同时管理多个 OKR 与执行任务的知识工作者
- 使用飞书多维表格管理任务、但缺乏可视化穿透视角的团队

### 1.4 技术架构

- **前端**：单个 HTML 文件，零外部依赖，vanilla JS + SVG
- **同步服务**：`sync_server.js`（Node.js HTTP 服务器，端口 9876），通过 lark-cli 与飞书多维表格交互
- **持久化**：浏览器 localStorage（离线模式）+ 飞书多维表格（同步模式）
- **兼容性**：现代浏览器 (Chrome / Edge / Firefox / Safari)

> **v4.0 变更**：同步服务器从 Python (`sync_server.py`) 迁移至 Node.js (`sync_server.js`)，与 lark-cli 共享运行时，提升稳定性。

## 2. 核心数据模型

### 2.1 四层层级系统

```
Object（大目标）
 ├── KR（关键结果）
 │   ├── Target（子目标）
 │   │   └── Task（任务）
 │   └── Target
 └── KR
     └── Target
         └── Task
```

| 层级 | 英文 | 语义 | 约束 |
|------|------|------|------|
| Object | 目标 | 顶层战略目标 | type='object'，parentId=null |
| KR | 关键结果 | 衡量 Object 达成的结果指标 | type='kr'，parent 只能是 object |
| Target | 子目标 | KR 的分解，阶段性里程碑 | type='target'，parent 只能是 kr 或 target |
| Task | 任务 | 可执行的原子工作单元 | type='task'，parent 可为任意上级 |

| 字段 | 类型 | 说明 |
|------|------|------|

### 2.3 时间戳系统（v4.0 新增）

**目的**：为每个实体对象提供全局唯一的不可变标识，用于同步冲突检测和数据追溯。

| 属性 | 说明 |
|------|------|
| 格式 | 14 位数字字符串，如 `20260628200300` |
| 生成时机 | 实体创建时（`addTask()` / `quickCreateParent()`）自动生成 |
| 不可变性 | 创建后只读，编辑弹窗中不可修改 |
| 唯一性保证 | `_tsUsed` 全局字典记录已用时间戳，冲突时自动递增直至唯一 |
| 数据迁移 | `loadData()` 中自动检测：无 timestamp 的旧数据从 `createdAt` 推导或调用 `makeTimestamp()` 补齐 |
| 飞书列名 | `时间戳(14位)` |

**`makeTimestamp()` 实现**：
```javascript
function makeTimestamp() {
  const now = new Date();
  const Y = now.getFullYear();
  const M = String(now.getMonth()+1).padStart(2,'0');
  const D = String(now.getDate()).padStart(2,'0');
  const H = String(now.getHours()).padStart(2,'0');
  const m = String(now.getMinutes()).padStart(2,'0');
  const S = String(now.getSeconds()).padStart(2,'0');
  let ts = parseInt('' + Y + M + D + H + m + S);
  while (_tsUsed[ts]) ts++;  // 冲突时递增
  _tsUsed[ts] = true;
  return String(ts);
}
```

### 2.6 归档维度（v4.4 规范化）

归档与状态是**两个正交维度**：一个任务可以是「已完成 + 已归档」，也可以是「进行中 + 未归档」。归档的语义是"从日常视野中收起"，而非"执行到了某个阶段"。

#### 2.6.1 统一判据函数

`isArchived` 字段可能来自多种数据源，实际值类型不统一：

| 来源 | 可能的值 |
|------|----------|
| 应用内勾选 | `true` / `false`（布尔） |
| 飞书多维表格同步 | `'true'` / `'false'`（字符串） |
| CSV 导入 | `'true'` / `'false'` / `'1'` / `'0'` / `''` |
| 旧版 localStorage | `undefined`（字段缺失） |

**问题**：字符串 `'false'` 在 JS 真值判断下为 **真**（`Boolean('false') === true`），若某处写 `if (t.isArchived)` 就会把未归档的行误判为已归档。

**规则**：全项目**禁止**直接对 `isArchived` 做真值判断，必须走统一判据函数：

```js
// app.js 顶部，声明在所有使用点之前（避开 let 的暂时性死区）
function isArchivedOf(t) {
  if (!t) return false;
  const v = t.isArchived;
  return v === true || v === 'true' || v === 1 || v === '1';
}
```

**双保险**：数据加载迁移层同时做归一化，把非布尔值统一转为真布尔，避免脏数据在内存中流转：

```js
if (typeof t.isArchived !== 'boolean') {
  t.isArchived = (t.isArchived === 'true' || t.isArchived === 1 || t.isArchived === '1');
  migrated = true;
}
```

**取反必须走判据函数**：`t.isArchived = !isArchivedOf(t)`。若写成 `t.isArchived = !t.isArchived`，当值为字符串 `'false'` 时 `!'false'` 得到 `false`，归档状态永远切不掉。

#### 2.6.2 一致性要求

**渲染出的 UI 控件状态必须与过滤器判据同源。** 曾出现的 bug：时间线表格的归档勾选框没有绑定 `checked` 属性，而过滤器用的是另一套判据，导致"行显示出来了但勾选框是空的"。

所有涉及 `isArchived` 的位置（过滤器、勾选框 `checked`、列筛选下拉的是/否取值、编辑弹窗初始化、统计计数）必须调用同一个 `isArchivedOf()`。

#### 2.6.3 三种归档显示模式

| 模式 | 状态变量 | 过滤逻辑 | 语义 |
|------|----------|----------|------|
| **默认** | 两者皆 false | `!isArchivedOf(t)` | 排除已归档 |
| **叠加** | `showArchived = true` | 不过滤 | 已归档混入正常内容一并显示 |
| **筛选** | `archiveOnly = true` | `isArchivedOf(t)` | 仅显示已归档 |

统一过滤表达式（所有视图共用）：

```js
archiveOnly ? isArchivedOf(t) : (!isArchivedOf(t) || showArchived)
```

**约束**：
- 「叠加」与「筛选」互斥——开启一个自动关闭另一个
- 两者独立于日期快速筛选组，可组合使用（如「筛选 + 今日待办」）
- 生效范围覆盖全部视图：任务列表、日历、时间线、时间线表格、优先级矩阵、团队看板

**入口**：📋 任务列表 tab

**功能**：

**侧边栏快速操作卡片（v4.1 新增，v4.4 重构）**：

分为两组，遵循不同的交互模型。

**第一组：日期筛选 + 时间线（严格互斥单选）**

| 按钮 | 元素 ID | 功能 | 徽章统计 |
|------|---------|------|----------|
| 📅 今日待办 | `qa-today` | 筛选今日截止的任务 | 今日截止且未完成的 task/schedule 数 |
| 📆 本周到期 | `qa-week` | 筛选本周截止的任务 | 本周截止且未完成数 |

**交互约束（v4.4 修正）**：这 4 个按钮同一时刻**只能点亮 1 个**。再次点击已点亮的按钮 = 取消该筛选，回到无筛选列表。切换主导航（仪表盘/日历/看板等）时自动清除点亮态。

**实现要求 — 单一状态变量**：所有按钮的 active 状态**只能由一个变量 `activeQuickFilter` 决定**（取值 `null | todayTodo | weekDue | monthDue | timelineTable`），用 map 遍历统一赋值：

```js
const map = { 'qa-today': 'todayTodo', 'qa-week': 'weekDue', 'qa-month': 'monthDue', 'qa-timeline-tl': 'timelineTable' };
Object.entries(map).forEach(([id, key]) => {
  document.getElementById(id)?.classList.toggle('active', activeQuickFilter === key);
});
```

> **反面案例（v4.3 及之前的 bug）**：原实现让每个按钮各看各的变量——「今日待办」看 `dateFilter`，「时间线」看 `currentView`，「已归档」看 `showArchived`。三套独立变量之间无法保证互斥，导致「时间线」和「本月到期」能同时点亮。
>
> **通用规则**：一组互斥的 UI 元素（tab / 单选按钮 / 筛选 chip），其点亮判据必须收敛到单一变量，绝不能每个元素判断各自的条件。

**第二组：归档模式（独立双 toggle，同一行并排）**

| 按钮 | 元素 ID | quickFilter 入参 | 状态变量 | 功能 |
|------|---------|------------------|----------|------|
| 📦 叠加 | `qa-archive-overlay` | `archiveOverlay` | `showArchived` | 已归档内容混入当前视图一并显示 |
| 🔍 筛选 | `qa-archive-filter` | `archiveFilter` | `archiveOnly` | 仅显示已归档内容 |

> 两者由 `quickFilter()` 最上方单独拦截处理，**不进入**第一组的 map 互斥逻辑。徽章 ID 为 `badge-archive-overlay`。

**交互约束**：
- 两者互斥（开启一个自动关闭另一个），再次点击 = 取消
- **不参与**第一组的互斥关系，可与日期筛选组合使用
- 切换第一组按钮时**不清除**归档状态（`clearAllFilters()` 不动 `showArchived` / `archiveOnly`）
- **在当前视图内生效**，不强制跳转到任务列表——在时间线视图点「筛选」，应在时间线内筛出已归档内容

> **实现要点**：归档分支调用 `renderAll()` 而非 `goToListView()`。`goToListView()` 仍保留给第一组的日期筛选按钮使用（日期筛选语义上必须回到列表才有意义）。

**视觉规范**：
- 激活态：紫色背景 + 白色文字 + 紫色阴影
- 未激活态：白色背景 + 灰色文字
- 徽章显示统计数字（仅统计 task 类型）

**布局规范（v4.4 新增）**：

侧边栏采用「头尾固定、中间滚动」的三段式布局，防止小窗口下底部按钮被系统任务栏遮挡：

| 区域 | 关键属性 | 作用 |
|------|----------|------|
| `.sidebar` | `height:100%` + `overflow:hidden` | 裁剪溢出，不外溢到屏幕外 |
| `.sidebar-nav` | `flex:1` + **`min-height:0`** + `overflow-y:auto` + `overflow-x:hidden` | 内容超高时区域内滚动 |
| `.sidebar-header` / `.sidebar-footer` | `flex-shrink:0` | Logo 与底部说明始终可见 |
| 滚动区内子项 | `flex-shrink:0` | 不被压扁，超高时触发滚动而非挤压 |

**两个必须遵守的细节**：
1. **`min-height:0` 不可省略** —— flex 子项默认 `min-height:auto`，缺这条 `overflow-y:auto` 完全不生效，内容照样撑开容器
2. **`overflow-x:hidden` 必须配套** —— `.quick-action-btn:hover` 有 `transform:translateX(4px)`，不挡住会在悬停时冒出横向滚动条

**高度响应式断点**：`@media (max-height: 760px)` 收紧 header / nav-item / divider / quick-action / footer 的 padding 与字号，内容总高从约 670px 降至约 538px。

> 原有响应式只有 `@media(max-width:768px)`（窄屏收成 60px 图标栏），对纵向空间不足零防护——这是底部内容被遮挡的根本原因。**侧边栏、固定工具栏等纵向堆叠较多的区域，宽度断点与高度断点都要有。**

**快速筛选栏**：

筛选栏分为三个分区，用颜色直观区分：

| 分区 | 内容 | 视觉样式 |
|------|------|----------|
| 类型筛选 | 🎯目标 / 📊KR / 🎯子目标 / 📋任务 胶囊按钮 | 选中时各自类型色（紫/蓝/青/灰） |

- Object/KR 实体按钮点击后筛选该实体及其所有下级（通过 ancestors 链匹配）

#### Object → KR 级联联动（v4.5 新增，v4.6 修正）

**背景问题**：原实现把**全部** KR 一次性平铺在筛选栏。KR 数量随目标增长线性膨胀，筛选栏被撑爆换行多次，且用户看到的大部分 KR 与当前关注的目标无关。

**KR 分两组处理**（由 `renderEntityFilterButtons()` 统一实现）：

##### A 组：归属明确的 KR（受目标门控）

能沿 `parentId` 链回溯到某个 Object 的 KR。

| 当前选中 | Object 分组 | A 组 KR |
|----------|-------------|---------|
| 无（`null`） | 全部显示 | **不显示**（连分组标签都不出现） |
| 某个 Object | 全部显示，选中项深紫点亮 | 只显示该 Object 名下的 KR |
| 某个 Object（名下无 KR） | 同上 | 显示灰字提示「📊 该目标下暂无 KR」 |
| 某个 KR | 全部显示，其父 Object 呈 **ctx 上下文态** | 显示同一 Object 下的**全部** KR（保持横向可切换），选中项深蓝点亮 |
| 其他类型（Target/Task 等） | 全部显示 | 不显示（无 Object 上下文） |

##### B 组：游离 KR（常驻显示，v4.6 新增）

**回溯不到任何 Object** 的 KR，包含三种形态：

| 形态 | 数据特征 | 成因 |
|------|----------|------|
| 上级为空 | `parentId === null / undefined / ''` | 手工创建时未选上级；飞书同步「父记录」列为空 |
| 上级已删除 | `parentId` 指向的 id 在 `tasks` 中不存在 | 删除 Object 时未级联清理子项 |
| 上级非 Object | 沿链回溯到根都没撞到 `type==='object'` | 层级录错，KR 挂在 Target 下 |

**规则**：这组 KR **一律常驻显示，不受目标选中状态门控**，渲染在筛选栏最末尾，用「⚠ 游离 KR」分组标签 + 琥珀色虚线边框标识。

> **为什么必须特殊处理**：v4.5 只做了 A 组逻辑，导致这三类 KR **在筛选栏永久失踪**——它们没有 Object 归属，用户永远找不到一个目标去「解锁」它们。用 Object 门控没有 Object 归属的 KR，前提本身就不成立。

**视觉设计**：

| 状态 | 样式 |
|------|------|
| 默认 | 琥珀底 `#FFFBEB` + 琥珀虚线边框 `#FCD34D` + 琥珀字 `#B45309` |
| 悬停 | 底色加深 `#FEF3C7`，提示「未关联上级目标，建议在编辑弹窗中补上级」 |
| 选中 | 深琥珀底 `#D97706` + **实线**边框 + 白字 |

> 虚线边框是「数据待补全」的视觉信号，引导用户去补上级；选中态改回实线，避免激活状态显得不确定。CSS 中 `.entity-kr-loose` 规则必须写在 `.entity-kr` **之后**，否则蓝色底会覆盖琥珀色。

**关键设计决策**：

1. **选中 KR 时保留同级 KR，而非只留选中的那一个**——用户在同一目标下横向对比 KR 是高频操作，若收敛成一个就必须先退回 Object 再重选，多两次点击。
2. **父 Object 用 ctx 态而非 active 态**——`active` 语义是「当前筛选条件」，选中 KR 时筛选条件是 KR 不是 Object。用独立的 `ctx` 类（浅紫底 + 紫色实线粗边框 + 字重 600 + `inset box-shadow`）表达「你正处在这个目标的上下文里」。JS 层强制互斥：`const isCtx = !isActive && ctxObjectId === o.id`。
3. **「暂无 KR」提示不可省**——若选中的 Object 名下没有 KR 就静默留白，用户会怀疑是 bug。
4. **游离 KR 排在最末尾**——不干扰主流程视线，但始终可达。
5. **B 组同样受 `hiddenFilters` 管辖**（列表视图）；若游离 KR 全被隐藏，分组标签也随之消失，不留空标签。

**归属判定实现**（`nearestObjectIdOf`）：

```js
// 沿 parentId 链向上找最近的 Object，找不到返回 null
// seen guard 防御环形引用：数据损坏时不死循环
function nearestObjectIdOf(node) {
  const seen = new Set();
  let cur = node;
  while (cur && cur.parentId != null && cur.parentId !== '') {
    if (seen.has(cur.id)) return null;      // 环形引用
    seen.add(cur.id);
    const p = tasks.find(x => x.id === cur.parentId);
    if (!p) return null;                    // 上级已删除，断链
    if (p.type === 'object') return p.id;
    cur = p;
  }
  return null;                              // 走到根都没撞到 Object
}
```

**性能**：结果预存进 `krOwner` Map（每个 KR 只回溯一次），避免在 A 组过滤时对每个 KR 重复走链。

**渲染顺序**：`🎯 Object` → `📊 KR`(A 组) → `⚠ 游离 KR`(B 组)。

**代码复用**：该逻辑原本在 4 个视图（任务列表 / 时间线正常态 / 时间线空态 / 团队看板）各写了一份，共约 80 行重复代码。v4.5 收敛为公共函数：

```js
renderEntityFilterButtons(activeId, toggleFn, useHidden)
```

| 参数 | 说明 |
|------|------|
| `activeId` | 该视图的实体筛选变量（`listEntityFilters` / `tlEntityFilters` / `boardEntityFilters`） |
| `toggleFn` | 点击回调函数名字符串（`'toggleEntityFilter'` / `'toggleTlEntityFilter'` / `'toggleBoardEntity'`） |
| `useHidden` | 是否应用 `hiddenFilters`（右键隐藏筛选功能）——**仅任务列表为 `true`**，其他视图无此功能 |

> **约定**：今后新增视图的实体筛选栏必须调用此函数，禁止再复制内联实现。四份重复代码是 bug 温床——任何一次规则调整都必须改 4 处，漏改必现不一致。

#### 实体按钮的状态与视觉规范（v4.7 新增）

**状态可见性与配色**

| 实体状态 | 筛选栏表现 | 配色 |
|---------|-----------|------|
| 已归档（`isArchivedOf(t) === true`） | **完全不显示** | — |
| 已取消（`status === 'cancel'`） | 显示但灰化 | 灰底 `#F3F4F6` + 灰字 `#9CA3AF` + 删除线 |
| 已完成（`status === 'done'`） | 显示，绿色 | 绿底 `#DCFCE7` + 深绿字 `#15803D` |
| 其他（待办/进行中/准备中/阻塞） | 显示，走本体配色 | 见下方三重编码 |

设计理由：
- **归档 = 从日常视野移走**。若已归档实体仍出现在筛选栏，等于归档没生效。要查看归档内容走「已归档」视图。
- **取消 ≠ 删除**。已取消的目标仍需可筛选（回溯历史决策），但视觉上必须明确「已作废」，故用灰化 + 删除线。
- **完成 ≠ 归档**。完成只是收尾，仍在关注范围内（可能要看结果、写复盘），故保留彩色而非灰化。

判定收敛为单一函数，禁止各按钮各判各的：
```js
function entityStateClass(t) {
  if (!t) return '';
  if (t.status === 'cancel') return 'entity-cancelled';
  if (t.status === 'done') return 'entity-done';
  return '';
}
```

**Object 与 KR 的三重视觉编码**

v4.6 之前两者仅靠浅底色区分（`#F5F3FF` vs `#EFF6FF`），差异过小，用户反馈「分不清哪个是目标哪个是关键结果」。v4.7 改为三个维度同时编码：

| 维度 | Object（目标） | KR（关键结果） |
|------|--------------|---------------|
| **形状** | 方角 `border-radius: 4px` | 胶囊 `border-radius: 16px` |
| **填充** | 深紫**实心** `#7C3AED` + 白字 | **白底 + 2px 蓝描边** `#60A5FA` + 蓝字 |
| **前缀符号** | `◆` | `▸` |
| **分组标签** | 紫底白字实心块 | 浅蓝底 + 蓝描边 |
| **选中态** | `#4C1D95` 更深紫 + 浅紫光圈 | `#2563EB` 蓝实心 + 浅蓝光圈 |

> **为什么用三重冗余编码**：单靠颜色区分对色弱用户无效，且在不同显示器/亮度下浅色差异会进一步压缩。形状（方 vs 圆）是最鲁棒的区分维度，实心/描边体现层级从属关系（Object 视觉重量更大 = 层级更高），前缀符号作为第三重兜底。

**CSS cascade 顺序要求**（踩坑记录）：
1. 状态修饰规则（`.entity-cancelled` / `.entity-done`）必须写在本体规则之后，且需 `!important`——因为 KR 的本体用了 `border: 2px solid` **简写**，简写会覆盖后续单独的 `border-color`。
2. `.tag-btn.highlighted`（右键黄色高亮标记）原先只改 `background` 不改 `color`。Object 改成白字后立刻出现**黄底白字不可读**。修复时必须同时指定 `color`，并单独处理 `.highlighted.active` 组合态。

**操作**：
- 点击行 → 打开编辑弹窗
- 悬停行 → 标题旁浮出快捷按钮：
  - Object：编辑属性 + 增加下级 KR
  - KR：编辑属性 + 增加下级 Target
  - Target：编辑属性 + 增加下级 Task
  - Task：编辑属性 + 增加后置 Task
- 增加下级：弹窗自动预填上级 + 层级类型，输标题即保存
- 增加后置 Task：创建同级同类型 Task（继承 `parent.type`），弹窗预填 parentId=同级、deps=[当前任务]；保存后自动同步原任务的 next 数组

### 3.3 关系图谱（分层展开模式）

**入口**：🔗 任务关系图谱 tab

**核心技术**：自研力导向模拟引擎（vanilla JS + SVG），分层展开模式

**分层展开机制**：

| 状态 | 默认显示 | 展开方式 |
|------|----------|----------|
| 初始 | 仅显示所有 Object 节点 | — |

- **节点**：圆角矩形，按层级递增大小
  - Object: 52px 高，紫色边框 3.5px
  - KR: 44px 高，蓝色边框 2.5px
  - Target: 38px 高，青色边框 2.5px
  - Task: 34px 高，灰色边框 2.5px
- 里程碑节点额外显示 ◆ 菱形标记及特殊边框样式
- 节点左上角：层级徽章（非 task 类型显示）
- 节点左上角：优先级圆点（重要紧急 红 / 重要不紧急 橙 / 紧急不重要 蓝 / 不紧急不重要 灰）
- 已展开节点显示「⊟」标记，未展开且有子节点显示「⊞」标记
- **层级边**：灰色虚线 `stroke-dasharray: 6 3`，无箭头
- **前置依赖边 (deps)**：橙色实线 + 箭头，重要紧急 相关边为红色加粗
- **后置关系边 (next)**：绿色虚线 `stroke-dasharray: 5 4` + 箭头
- **tooltip**：悬停显示详细信息

**交互**：
| 操作 | 行为 |
|------|------|
| 悬停节点 | 显示 tooltip |
| 拖拽节点 | 移动节点位置，松手后力模拟收敛 |
| 点击节点 | 展开/收起下级 |
| 点击节点（已展开） | 收起下级 + 取消高亮 |
| 双击节点 | 打开编辑弹窗 |
| 鼠标滚轮 | 缩放图谱（Cmd/Ctrl + 滚轮），普通滚轮正常滚动页面 |
| Cmd/Ctrl + 拖拽空白 | 平移画布 |

**力模拟引擎**：
- 持续动画循环 (`requestAnimationFrame`)
- alpha 从 1.0 冷却至 0.005，衰减系数 0.008
- 全节点对斥力：`12000 × alpha / dist²`
- 层级边吸引力：目标长度 130px，强度 0.08
- 依赖边吸引力：目标长度 200px，强度 0.03
- 碰撞检测：节点间最小间距 = (collideA + collideB)/2 + 6
- 中心引力：`0.003 × alpha`
- 阻尼系数：0.75
- 拖拽时将节点固定，重置速度，重燃 alpha ≥ 0.3
- 切换视图时自动停止模拟

### 3.6 层级健康度检查面板（v4.7 新增）

**设计动因**：`parentId` 字段无强制约束，加上 CSV 导入 / 飞书同步两条外部写入通道长期缺少校验，数据集会静默积累结构性损坏——悬空引用、环形引用、重复 ID、`children` 索引与 `parentId` 不一致等。这些问题在 UI 上表现为「某个任务突然不显示」「树形展开卡死」，但用户无法定位根因。本面板把隐性损坏显性化，并提供可选修复。

**入口**：顶栏 `🩺 健康检查` 按钮。按钮上挂红点角标 `health-badge`，显示当前 P0+P1 问题数；无问题时角标隐藏。

#### 3.6.1 检查引擎

`checkHierarchyHealth(list)` 是**纯函数**：只读传入数组，不碰 DOM、不落盘、不改数据。返回问题数组：

```js
[{ code, severity, title, detail, ids, fix }]
```

- `code` — 问题编码（如 `C1` / `H3` / `M5` / `L12`），用于测试断言与去重
- `severity` — `P0` 致命 / `P1` 严重 / `P2` 索引一致性 / `P3` 业务语义
- `ids` — 涉及的实体 ID 数组，面板上渲染为可点击跳转链接
- `fix` — 可选的 `{ label, apply() }`。`apply()` **只改内存对象**，不调 `saveData()` / `renderAll()`

性能：预建 `byId` Map 索引，避免 O(n²) 扫描。环形数据经测试在 100ms 内返回，不死循环。

#### 3.6.2 39 项检查清单

**P0 致命（5 项）** — 会导致渲染死循环或数据不可用

| 编码 | 检查项 | 可修复 |
|------|--------|--------|
| C1 | 自引用（`parentId === id`） | ✅ 置 `null` |
| C2 | 环形引用（A→B→C→A） | ✅ 断开环中最深一环 |
| C3 | 重复 ID | ✅ 重新分配后来者 ID |
| C4 | ID 非法（非正整数 / `NaN`） | ✅ 分配新 ID |
| C5 | `type` 非法（不在七种合法类型内） | ✅ 归为 `task` |

**P1 严重（6 项）** — 层级结构被破坏

| 编码 | 检查项 | 可修复 |
|------|--------|--------|
| H1 | 悬空 `parentId`（指向不存在的 ID） | ✅ 置 `null` |
| H2 | `Task` 父类型非法（挂在 `record` / `idea` 等下） | ✅ 置 `null` |
| H3 | `KR` / `Target` 父类型非法 | ✅ 置 `null` |
| H4 | `parentId` 为非数字字符串 | ✅ 数字化或置 `null` |
| H5 | `Object` 有上级 | ✅ 置 `null` |
| H6 | 游离 KR / 游离 Target（无上级） | ⚠️ 仅提示，需人工指定归属 |

**P2 索引一致性（12 项）** — 派生字段与源字段不同步

覆盖 `children` 数组与 `parentId` 双向不一致（多出、缺失、重复、含自身、含不存在 ID）、`deps` / `next` 悬空引用与环、`nextId` 小于现有最大 ID、`timestamp` 缺失或重复。多数可自动修复（重建索引 / 剔除非法项 / 校正 `nextId` / 补 `makeTimestamp()`）。

**P3 业务语义（16 项）** — 不影响运行但违反业务约定

覆盖 `status` / `priority` / `progress` 取值非法、`isArchived` 非布尔、进度与状态矛盾（如 `done` 但 `progress<100`）、日期格式非法、`startDate > deadline` 倒挂、子任务期限超出父级、标题为空、已逾期未完成、空壳 KR（无任何下级）等。

#### 3.6.3 父类型白名单

```js
const ALLOWED_PARENTS = {
  object: [],                              // Object 是根，不允许有上级
  kr:     ['object'],
  target: ['kr', 'object'],
  task:   ['target', 'kr', 'object'],
  record: '*',                             // '*' = 不限制
  schedule: '*',
  idea:   '*'
};
```

`record` / `schedule` / `idea` 是**附属信息**，不参与 OKR 层级树，因此不做父类型限制——这是产品决策，不是漏检。

#### 3.6.4 修复流程与快照机制

修复采取「勾选后批量修复 + 自动备份」模式：

1. 用户在面板上按项勾选，或点分组标题旁的「全选本组」
2. 点「修复选中项」→ **先写快照**：`localStorage['ai-task-lens-health-snapshot']` 存入修复前的完整 `tasks` 数组
3. 快照写入失败（如 `QuotaExceededError`）→ **中止修复**，不冒无备份修改数据的风险
4. 按固定顺序执行 `fix.apply()`，全部只改内存
5. 末尾统一 `rebuildChildren()` + 校正 `nextId` → 一次 `saveData()` → 一次 `renderAll()`
6. 面板顶部出现「撤销本次修复」按钮，调 `undoHealthFix()` 从快照回滚

**修复顺序**（先归一化再修结构，避免用脏数据判断脏数据）：

```
C4/C5（ID/type 归一化）
  → H4/H5（parentId 数字化）
  → H1/H3/H2（悬空 / 非法父类型）
  → C1/C2（环 / 重复 ID）
  → M*（索引一致性）
  → L*（业务语义）
  → rebuildChildren() + 校正 nextId
```

**快照策略**：只保留最近一次快照。多份历史会逼近 localStorage 5MB 上限，且用户实际只需要「刚才那次改错了」的回退能力。

#### 3.6.5 导入侧联动

CSV 导入完成后自动跑一次健康检查，若有 P0/P1 问题则直接弹面板。同时导入解析层已补：

- `parentId` 加 `Number.isFinite` 守卫（`parseInt('abc')` → `NaN` 不再落库）
- `type` / `priority` / `status` 走枚举白名单，非法值回落到默认值
- `timestamp` 改用 `makeTimestamp()`，不再误用数字 `id`
- 导入后统计纠正次数，toast 告知用户「已自动净化 N 处非法字段」

### 4.1.1 周期任务（v5.2/R3.2 重构：批量创建独立任务）

**适用范围**：仅 `task` / `schedule` 两种类型；切换到其他类型时该开关隐藏并自动复位。**编辑已有任务时 checkbox 禁用**（仅新建可用）。

**核心模型**：创建时批量生成多个**完全独立的任务**，每个有独立 id/timestamp/deadline/status。创建后各任务与普通任务完全一致，可独立编辑/删除/完成/归档。`recurringGroupId` 字段（14 位时间戳）作为同批软关联标记。

**两条原则**：
1. **开始日期 = 截止日期**：勾选「🔁 周期任务」时开始日期强制同步为截止日期；周期态下两字段双向联动（改任一同步另一，`syncRecurringDates`）；取消勾选解除锁定。
2. **多次日期 = 默认手动点选，规则手动触发**：勾选后**不自动生成任何日期**，由用户自己决定。

**频率规则**（`_readRecurRuleFromForm` 读表单 → `generateRecurringDates(rule, start, end)` 纯函数生成）：
- 每天：逐日 + `interval` 间隔
- 每周：多选周一~周日，仅选中星期入集合
- 每月：选 1~31 号；当月无该日（如 31 号遇 2 月）自动跳过
- 缺省 `end` 时生成至开始日期 + 90 天
- **仅当用户点击「⚡ 按规则生成」按钮（`_applyRecurRule`）时才生成**

**迷你月历**（`renderMiniCalendar`，42 格周一起始网格，◀ ▶ 今天导航）：
- 默认空白，由用户逐个点击勾选；紫底（`.mini-auto`）= 规则生成、浅紫（`.mini-selected`）= 手动添加
- 点击日期：加入 / 移出集合
- 已选日期以 chips（`.recur-chip`）展示，可逐个删除

**批量创建**（`saveTask` 周期模式）：遍历 `_recurDateList()` 每个日期，创建独立任务（`Object.assign({}, data, {deadline: ds, startDate: ds, recurringGroupId: groupId})`），共享 `groupId = makeTimestamp()`，每个独立 `nextId++` + `makeTimestamp()`；只 `saveData()` + `renderAll()` 一次。单批上限 365 个。

**编辑已有批次成员**：checkbox disabled，显示批次提示条（`recurring-batch-bar`）：「此任务属于周期批次（共 N 个）」+ [查看同批] + [批量删除]。`viewRecurringBatch(groupId)` 弹窗列出同批任务，`deleteRecurringBatch(groupId)` 确认后批量删除。

**数据迁移 v4→v5**：`isRecurring=true + dates` 展开为多个独立任务（`doneDates[ds]` 映射为 `status='done'`），删除原实体；普通任务补 `recurringGroupId=null`，删除四字段。

### 5.4 前端同步功能

**按钮位置**：顶部工具栏

| 按钮 | 功能 | 交互 |
|------|------|------|
| 🔄 飞书→本地 | 拉取飞书数据覆盖本地 | 点击 → 进度面板显示 → toast 提示结果 |
| 📤 本地→飞书 | 推送本地数据到飞书 | 点击 → confirm 确认 → 进度面板显示 → toast 提示结果 |

**pull 流程**：
1. `fetch(SYNC_SERVER + '/pull', { method: 'POST' })`
2. 获取 `requestId`，调用 `startProgressPolling(requestId)`
3. 解析返回的 `entities` 数组
4. 清空所有 `children`，根据 `parentId` 重建层级关系
5. `parentId` 统一转 `Number()`
6. **v4.0**：时间戳冲突检测（详见 5.5）
7. 计算 `nextId = max(id) + 1`
8. 设置 `dataSource = 'feishu'`，保存到 localStorage
9. `renderAll()` 刷新所有视图
10. `stopProgressPolling()` 停止轮询

**push 流程**：
1. `confirm('确定将本地数据推送到飞书？')`
2. `fetch(SYNC_SERVER + '/push', { method: 'POST', body: { entities: tasks } })`
3. 获取 `requestId`，调用 `startProgressPolling(requestId)`
4. 解析返回的 `feishuIds` 对象
5. 用 `Object.entries().forEach()` 遍历，写入 `t.feishuRecordId`
6. `saveData()` 持久化
7. `stopProgressPolling()` 停止轮询

**防重入**：`syncInProgress` 全局标志，同步中禁用按钮

### 5.5 时间戳双向同步与冲突检测（v4.0 新增）

**Pull 方向（飞书 → 本地）**：
- 服务器从飞书 `时间戳(14位)` 列读取数据，写入实体 `timestamp` 字段
- 新记录（本地不存在）→ 直接导入，时间戳一并同步
- 旧记录（本地已存在）→ 比较时间戳：
  - 时间戳一致 → 正常合并
  - **时间戳不一致** → 记录到 `timestampConflicts` 数组

**Push 方向（本地 → 飞书）**：
- 服务器在创建/更新 KR 和 Task 时，将 `timestamp` 写入飞书 `时间戳(14位)` 列
- 新记录 → 带时间戳创建
- 已有记录 → 带时间戳更新

**冲突处理**：
- 拉取完成后，若 `timestampConflicts` 非空，弹出 alert 显示冲突详情：
  ```
  ⚠️ 时间戳冲突检测
  
  以下 N 条记录的本地时间戳与飞书不一致：
  
  · "任务标题A"
    本地：20260628143000
    飞书：20260628120000
  
  · "任务标题B"
    本地：20260628150000
    飞书：20260628160000
  
  请确认数据来源后手动处理。
  ```
- 冲突不阻断同步流程，仅提醒用户

## 12. 工程约定与自测规范（v4.4 新增）

### 12.1 UI 状态类 bug 必须做 DOM 级验证

纯状态逻辑测试**测不出** UI 点亮 bug —— 互斥点亮的根因在 `classList.toggle()` 那一层，状态变量本身是对的。

**做法**：用 JS 对象模拟 `document.getElementById` 与 `classList`，把真实的 `updateQuickActionStates()` 抄进测试脚本跑断言。

**必须断言的项**：
- 「点亮的元素数量 === 1」（互斥组）
- 全排列切换组合（5 个按钮 × 4 种前置状态）
- 再次点击 = 取消
- 切换主导航后点亮态被清除

### 12.2 布尔字段测试的最小输入集

任何可能来自外部导入的布尔字段，测试必须覆盖至少 9 种输入：

`true` / `'true'` / `1` / `'1'` / `false` / `'false'` / `''` / `undefined` / 字段缺失

并额外核对：**渲染出的控件状态（`checked`）与过滤器判据结果逐行一致**。

### 12.3 层级依赖的 UI 门控必须先问「门控前提是否总成立」

**教训来源**：v4.5 做「选中目标才显示其下 KR」，漏了「有些 KR 根本没有目标归属」这一类，导致它们在筛选栏永久失踪（v4.6 修复）。

**通用规则**：当 UI 用 A 的选中状态去门控 B 的可见性时，必须先枚举 **B 找不到对应 A** 的所有情况：

| 检查项 | 本项目对应的具体形态 |
|--------|---------------------|
| 关联字段为空 | `parentId` 为 `null` / `undefined` / `''` |
| 关联字段指向已删除对象 | `parentId` 指向的 id 不在 `tasks` 中 |
| 关联字段指向了错误类型 | KR 挂在 Target 下，回溯到根都没遇到 Object |
| 关联形成环 | A→B→A，回溯逻辑需 `seen` guard，否则死循环 |

**处理原则**：这类「无归属」数据**不能直接隐藏**——用户会认为数据丢了。正确做法是**单独分组常驻显示 + 视觉上标记为待补全状态**，同时引导用户修数据。

**测试要求**：门控类功能的测试数据必须包含上述每一种畸形形态，不能只造「理想层级」。

### 12.4 CSS 变体类的 cascade 顺序

新增基础类的变体（如 `.entity-kr` → `.entity-kr-loose`）时，变体规则**必须写在基础规则之后**，否则基础规则的背景色/边框会覆盖变体。

验证方法：断言两条规则在文件中的 `indexOf` 位置关系，而非仅断言变体规则存在。

**v4.7 追加两条踩坑**：

| 坑 | 说明 | 对策 |
|----|------|------|
| `!important` 压不住 `border` 简写 | KR 本体写了 `border: 2px solid #60A5FA` 简写，后续状态规则单独给 `border-color` 无法覆盖简写整体 | 状态规则加 `!important` 并显式补 `border-style: solid` |
| 改了实体配色必须同步检查所有覆盖态 | Object 从深底改白字后，右键黄色高亮（只改 `background` 不改 `color`）立刻出现「黄底白字」不可读 | 凡改 `color` 的规则，须回查所有会覆盖 `background` 的 class（`highlighted` / `active` / 及其组合态） |

### 12.5 纯逻辑函数的测试桩策略

`checkHierarchyHealth()` 这类纯函数的测试**不重写一份逻辑自测自己**——那只能证明「我抄对了」，不能证明生产代码对。

做法（见 `_test_health_helper.js`）：

1. 用正则从 `app.js` 中**提取真实函数源码**
2. 用 `new Function(depsList, source + '; return fn;')` 注入桩依赖（`TYPE_LABELS` / `makeTimestamp` 等）
3. 拿到的就是生产环境同一份逻辑，再对它做断言

同理适用于 `renderEntityFilterButtons()` 这类摸 DOM 的函数——用 JS 对象模拟 `document.getElementById` + `classList`，把真实函数抄进桩里跑。

### 12.6 CSS 布局改动的验证方式

不硬编码期望值，而是**解析真实 `style.css`** 校验：

| 验证项 | 方法 |
|--------|------|
| 属性存在性 | 正则提取规则块，断言 `min-height:0` / `overflow-y:auto` 等确实存在 |
| 大括号平衡 | 逐字符扫描计数，深度必须归零 |
| cascade 冲突 | 检查目标规则之后是否有同选择器规则覆盖 |
| 多窗口高度 | 用内容高度模型扫描 8 档高度（1040 → 480px），确认均不溢出 |
| 旧断点未破坏 | 断言原 `@media(max-width:768px)` 规则仍完整 |
